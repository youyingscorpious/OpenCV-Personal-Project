# 01 · 算法设计：路口「停车 → 色卡识别」闸门

> 方案 A —— 纯导航端闸门，零协议改动。
> 所有结论都可以在现有代码里逐条核对，引用行号对应本次改动前的仓库状态。

---

## 1. 问题陈述

赛程阶段二的链路是：

```
车沿主线循迹 ──▶ 到达三岔路口 ──▶ 识别色卡（红/黄/蓝）──▶ 驶入对应支路
```

规则 4.2 要求「**停在三岔路口 → 识别色卡 → 驶入对应支路**」，7.3.6 对「未停车直接冲过」单独扣分。

现有 `robopioneers_competition` 已经补上了「路口定角转向」与「等待期间零速保持」，但**颜色是被"随时"接收的**：

```python
# route_controller.py:253  _select_route()  （改动前的行为）
self.selected_route = color          # ← 行进中（LINE_FOLLOW）就把颜色写死
...
# route_controller.py:329  _junction_tick()
if self.selected_route in (1, 2, 3):
    self._begin_turn(now)            # ← 到路口只要非空就立刻转向
```

由此产生三个具体后果：

1. **决策依据错位**：转向用的是"整个赛程中第一次见到的那个颜色"——可能是几十分米外的色卡，也可能是阶段三那块**红色 STOP 牌**。
2. **没有停稳门限**：转向指令与"车是否真的停住"完全解耦，`WAIT_ROUTE_MANEUVER` 里那套"连续 N 帧零速 + 驻留时间"的判据只在 `WAIT_MOTOR_STOP`（STOP 牌）用过。
3. **单帧决定去向**：板端 10 Hz 推帧，一帧检测抖动就能定路，没有去抖。

本设计把链路改造成显式的三拍握手：

```
电机循迹完成 ─▶ ①导航→电控 停车 ─▶ ②停稳证据 ─▶ ③识别窗口 ─▶ ④多帧投票 ─▶ 转向
```

## 2. 设计不变量

这五条是后面所有细节的裁决依据，实现时必须逐条成立。

| 编号 | 不变量 | 违反的表现 |
|---|---|---|
| **I1** | 任何转向指令发出前，必须已向电控端发过停车帧，**且**取得停稳证据（或显式降级） | 车还在动就原地差速转，压线、丢帧、撞架子 |
| **I2** | 行进期间产生的任何颜色观测**不得**进入本轮选路决策 | 选到几十米外的色卡或红色 STOP 牌 |
| **I3** | 一轮路口只锁一次颜色，锁定后不可改写 | 抖动导致支路来回切换 |
| **I4** | 每个等待都有上界，上界到达后有**确定动作**，不引入新的死等 | 车停在路口不动，赛程卡死 |
| **I5** | 不改原包文件、不改通信参数、不新增电控命令字 | 与规则 6.1 / 7.3.3 冲突，且无法回退 |

> I4 特别重要。闸门是"新增的等待"，如果不给上界，就把"选错路"的风险换成了"整个赛程卡死"的风险——那是更差的交易。

## 3. 与现有状态机的关系

导航状态 `self.state` 仍然是原包那张表（`TRANSITIONS`，[navigation_node.py:22](../robopioneers_navigation/robopioneers_navigation/navigation_node.py#L22)）：

```
WAIT_START ──START──▶ LINE_FOLLOW ──JUNCTION_DETECTED──▶ WAIT_ROUTE_MANEUVER
                            │                                     │
                            └──ROUTE_SELECTED──▶ ROUTE_FOLLOW ◀──┘(本方案补的边)
```

**闸门不新增 state**，只在 `WAIT_ROUTE_MANEUVER` 内部维护一个**子相位**（gate phase），由 4 个字段表达：

```python
_stop_confirmed : bool     # 停稳证据是否已达标
_color_window_open : bool  # 识别窗口是否打开（= _stop_confirmed，保留独立字段便于观测）
_vote_color : int          # 当前投票候选色
_vote_count : int          # 连续同色帧数
```

### 3.1 闸门相位表

| 相位 | 判定条件 | 颜色帧处理 | 底盘 |
|---|---|---|---|
| **G0 CLOSED** | `state ∈ {LINE_FOLLOW, ROUTE_FOLLOW}` | **丢弃**（fallback 关闭时） | 电机板本地 PID 循迹 |
| **G1 ARMING** | `state == WAIT_ROUTE_MANEUVER ∧ ¬_stop_confirmed` | **丢弃** | 20 Hz 零速保持 |
| **G2 OPEN** | `state == WAIT_ROUTE_MANEUVER ∧ _stop_confirmed ∧ ¬locked` | 投票 | 20 Hz 零速保持 |
| **G3 LOCKED** | 投票达标，`selected_route` 已写入 | **丢弃** | 定角转向 |
| **G4 DONE** | `_finish_turn()` 完成，进入 `ROUTE_FOLLOW` | 丢弃（`state==ROUTE_FOLLOW` 早退） | 恢复 `CMD_LINE` |

### 3.2 全序关系（必须严格成立）

```
G0 ──(路口事件)──▶ G1 ──(停稳证据 / 超时降级)──▶ G2 ──(投票)──▶ G3 ──(转到角)──▶ G4
```

不允许的跳转：

- `G1 → G3`：未停稳就锁定颜色 —— 违反 I1。
- `G0 → G2`：行进中就投票 —— 违反 I2。
- `G3 → 任何非 G4`：锁定后重开窗口 —— 违反 I3。

## 4. 三个判据

### 4.1 判据一：停稳证据（G1 → G2 的唯一凭据）

**输入**：电机板 `0x10` 状态帧，`DATA = <h h B>` = 左轮实测 mm/s、右轮实测 mm/s、状态。
按 [MCU_INTERFACE.md:26](../robopioneers_navigation/docs/MCU_INTERFACE.md#L26)，该帧约每 **100 ms** 一帧。

**单帧判据**：

```
stopped(frame) ⟺ fresh(Δt ≤ 0.25 s)
                ∧ state ∈ {STATE_IDLE=0, STATE_JUNCTION=6}
                ∧ |v_L| ≤ stopped_speed_threshold
                ∧ |v_R| ≤ stopped_speed_threshold
```

**连续判据**：

```
confirmed ⟺ 连续 N 帧 stopped ∧ (t_now − t_first_stopped) ≥ dwell
```

默认 `N = 3`、`dwell = 0.25 s`、`threshold = 10 mm/s`（沿用原包 `stopped_speed_threshold`）。

#### 为什么 `state ∈ {0, 6}` 而不是只认 `0`

`STATE_JUNCTION=6` 就是固件的「路口已刹停」态：全黑路口时电机板刹停并置 6（见
[MCU_INTERFACE.md:50](../robopioneers_navigation/docs/MCU_INTERFACE.md#L50)）。部分固件在路口会**持续锁存 6 而不回 IDLE**。
若只认 IDLE，这类固件上闸门必然超时。两者都接受，再叠加轮速阈值，语义仍然严格。

#### 为什么 `fresh ≤ 0.25 s`

`0x10` 是 100 ms 一帧，0.25 s 允许丢 2 帧。取和原包 `line_status_time` 一致的量级，避免把"链路已经断了"误判成"车停着"。

#### 为什么**不复用** parent 的 `stopped_samples`

原包在 `_handle_motor_frame()` 里用 `self.stopped_samples` / `self.stopped_since` 给 `WAIT_MOTOR_STOP` 做停稳计数
（[navigation_node.py:688](../robopioneers_navigation/robopioneers_navigation/navigation_node.py#L688)）。那两个字段是 **`WAIT_MOTOR_STOP` 的私有状态**：进入该状态前会被清零，条件不满足时会被重置。

如果路口闸门复用它们，会出现两种互相污染：

- 路口阶段的计数残留，被 `WAIT_MOTOR_STOP` 当成自己的样本（提前启动机械臂）；
- 反之亦然。

因此闸门使用**独立字段** `_stop_confirm_samples` / `_stop_confirm_since`，与 parent 零耦合。

#### `motor_status_is_measured = false` 时的处理

该参数为 false 表示 `0x10` 的速度字段不是编码器实测值（原包用它来锁死 `WAIT_MOTOR_STOP`，
见 [navigation_node.py:240](../robopioneers_navigation/robopioneers_navigation/navigation_node.py#L240)）。
此时轮速不可信，闸门降级为 **state-only 判据**：只要 `state ∈ {0, 6}` 连续 N 帧即算停稳。
这一降级必须在日志里明确打印，因为它把安全等级降低了。

### 4.2 判据二：识别窗口（G2）

**定义**（状态谓词形式）：

```
window_open(t) ⟺ state(t) == WAIT_ROUTE_MANEUVER ∧ _stop_confirmed(t)
```

它**等价于**时间区间：

```
[t_confirm , t_confirm + route_junction_color_wait_s]
```

因为 `_stop_confirmed` 只在 `_confirm_stopped()` 置真，而该状态必然在 `route_junction_color_wait_s`
（默认 8 s，原包既有参数）耗尽时以 `FAULT` 结束。

#### 为什么用状态谓词而不是真做一个定时器

1. **零额外时钟源**：所有判定挂在已有的 20 ms `enh_timer` 上，不引入第二个定时器导致的竞态。
2. **天然幂等**：重复进入 `WAIT_ROUTE_MANEUVER`（固件锁存路口事件）会自动重新判定，不需要清理定时器。
3. **可观测**：窗口状态就是两个布尔量，直接进 `/navigation/competition/status`。

#### 窗口内的帧来源

视觉端是**推送模型**：板端 `main_vision.py` 以 10 Hz 推 `0x01 TARGET_LIST`（[main_vision.py:47](../robopioneers_vision_tcp/board/main_vision.py#L47)），
PC 桥接以 20 Hz 推同款帧。导航端从不"请求"一帧，只决定"采信哪一帧"。

窗口打开后，帧的**新鲜度**由原包已有的 `_check_vision_timeout()`
（[navigation_node.py:1105](../robopioneers_navigation/robopioneers_navigation/navigation_node.py#L1105)）保证——
不过它只在 `LINE_FOLLOW / ROUTE_FOLLOW` 生效，因此窗口内需要独立的**时钟新鲜度保护**（见 §6 降级矩阵 D4）。

### 4.3 判据三：颜色投票（G2 → G3）

只有 `color ∈ {1,2,3}` 的帧会进入投票（原包的 `_select_route_color()` 已经把 `color_valid=false` 的帧过滤成 `None`，
`_select_route()` 根本不会被调用）。

```
if color == _vote_color and (now − _vote_ts) ≤ vote_timeout:
    _vote_count += 1
else:
    _vote_color, _vote_count = color, 1
_vote_ts = now
lock ⟺ _vote_count ≥ M
```

默认 `M = 3`、`vote_timeout = 0.6 s`。

#### 为什么用"连续同色"而不是"多数票"

| 方案 | 优点 | 缺点 |
|---|---|---|
| **连续同色（选用）** | 状态 O(1)、确定性、零缓冲；超时自动失效，不会把早期错误帧算进票仓 | 对"颜色反复跳变"不收敛 |
| 滑窗多数票 | 抗随机抖动更强 | 需要环形缓冲；窗口内混入红灯牌/远处色卡时仍然"多数通过"，反而掩盖 I2 |
| 置信度加权 | 用上协议里的 confidence 字段 | 板端当前恒填常量（`confidence=200`），加权无意义 |

关键理由：**I2 要求的是"这段时间内看到的是同一张卡"，不是"历史上看到最多的是哪个"**。连续同色正好表达这个语义，而多数票会在"行进中看到 3 帧红 + 停下后看到 2 帧蓝"时选红——恰好是我们想消除的错误。

`vote_timeout` 的作用：如果颜色帧断流（视觉抖动、板端丢帧），投票自动过期，避免"跨窗口累积"。

## 5. 时序预算

假设固件 `0x10` 100 ms/帧、板端目标列表 10 Hz：

| 环节 | 触发 | 典型耗时 | 上界 |
|---|---|---|---|
| 路口事件 → 停车帧下发 | `_on_enter(WAIT_ROUTE_MANEUVER)` | ≤ 20 ms（同一 tick） | 20 ms（串口写超时 50 ms） |
| 电机制动 | 固件 | 100–300 ms | —（由闸门兜住） |
| 停稳确认 | 3 帧 ×100 ms + dwell 0.25 s | **0.25–0.55 s** | `junction_stop_confirm_timeout_s` = 2.0 s |
| 识别窗口 → 锁定 | 3 帧 @10 Hz | **≈ 0.3 s** | `route_junction_color_wait_s` = 8.0 s |
| 定角转向 | `_turn_tick` | 0.5–2 s | `route_turn_timeout_s` = 4.0 s |
| 到角稳定 | `_turn_phase=settling` | 0.25 s | `route_turn_settle_s` |

**整段路口停留**典型 **1.0–1.5 s**（改造前约 0.6–1.0 s），多出来的部分基本就是"确认停稳 + 去抖"的成本。
这 0.5 s 换来的是"不选错支路 + 不打滑转向"，对总成绩是正收益。

## 6. 超时与降级矩阵

| 编号 | 条件 | 动作 | 理由 |
|---|---|---|---|
| **D1** | 停稳确认超时（`junction_stop_confirm_timeout_s`，默认 2.0 s） | `timeout_action=proceed` → 告警 + 强制开窗；`fault` → `FAULT` | 默认 **proceed**：改造前的行为本来就是"不确认直接转"，proceed 与之等效，**不新增失败点**。信任遥测的队伍可切 `fault` |
| **D2** | `0x10` 遥测缺失 / 过期 | 单帧判据恒假 → 走 D1 | 链路断了不等于车在动，但不能假设车停着 |
| **D3** | `motor_status_is_measured=false` | 降级为 state-only 判据，日志告警 | 轮速不可信，只能信状态码 |
| **D4** | 窗口内视觉断流 | 不立刻 FAULT；继续零速保持，直到 `route_junction_color_wait_s` 耗尽 → `FAULT` | 原包在路口状态本就不监控视觉超时（`_check_vision_timeout` 只管循迹态）。保持"停在原地等"比"急停"更安全，且有 8 s 上界 |
| **D5** | 禁止进入 `ROUTE_FOLLOW` 后的重复转向 | `_route_done` + `_maneuver_done_once` 双锁 | I3 |
| **D6** | 转向完成后固件仍锁存路口事件 | `route_junction_ignore_s` 屏蔽窗口（原包已有） | 已有机制，闸门不干扰 |
| **D7** | fallback：`route_turn_on_color_without_junction=true` | 闸门在 `LINE_FOLLOW` 放行，但**仍要求投票**；不停车直接开窗 | 这是显式开启的应急路径，语义上允许 G0→G2 |

> D1 的默认值选择是本方案最重要的工程决策：**闸门是"加固"，不是"新门禁"**。默认不能因为加固失败而让整车不可用。

## 9. 为什么"开窗"就等价于"调用色卡识别模块"

这是本方案最需要讲清的一点，因为需求原文是"**调用**色卡识别模块"。

视觉端在当前架构里是**推送模型**，不是请求-应答模型：

```
板端：每帧 snapshot() → detect() → 10 Hz 推 TARGET_LIST
桥接：每 tick 调 nav_vision.color()/stop() → 20 Hz 推 TARGET_LIST
导航：被动接收，从不发请求
```

板端确实有下行命令字 `CMD_START=0x81` / `CMD_STOP=0x82`
（[vision_comm.py:36](../robopioneers_vision_tcp/board/vision_comm.py#L36)、解析在
[vision_comm.py:315](../robopioneers_vision_tcp/board/vision_comm.py#L315)），但：

- 它走 **TCP**，而 `ENABLE_TCP_SERVER=False`（[vision_comm.py:45](../robopioneers_vision_tcp/board/vision_comm.py#L45)），当前根本没监听；
- `enabled` 一旦为 false，**目标列表整条停发**，导航端 0.6 s 视觉超时（`vision_source_timeout_seconds`）会立刻 `FAULT` —— 车在循迹途中就急停。

所以"真下发"能做的只有"帧照发、颜色压成 0"，而这件事在导航端做成本为 0，在板端做要加 UDP 收包 + 绑定 5000 + 新命令字 + 重烧固件。

**结论**：在推送模型下，"调用识别"能被观察到的唯一语义就是"**决定是否采信此刻的结果**"。把"调用"实现为"采信闸门"，
因果顺序与真实调用完全一致（停车 → 停稳 → 才开始用颜色 → 用完即关），且：

- 不新增下行通道，不改帧格式，不重烧固件；
- 对视觉端零侵入（板端、桥接、回放三种跑法都一样）；
- 视觉端将来换成真行触发时，导航端判定逻辑不需要改。

## 10. 复杂度与时序确定性

- 每个 20 ms tick 的闸门开销：**O(1)**，无内存分配（除限频日志的字符串），无阻塞调用。
- 不新增线程、不新增定时器、不新增 socket。
- 所有判定只读 `self.motor_status` / `self.state` / `self.selected_route` 等已有字段，无锁需求（单线程 rclpy 回调）。
- 状态迁移全部幂等：重复的路口事件、重复的颜色帧、重复的 tick 都收敛到同一相位。
